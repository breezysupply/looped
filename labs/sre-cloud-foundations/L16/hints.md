# L16 hints (four rungs; rungs 3–4 end independent credit for this attempt)

1. **Boundary.** The application is healthy inside every pod; the request dies somewhere between the client and a pod. Walk the hops in order — Service selector, EndpointSlice endpoints, endpoint port, endpoint readiness — and stop at the first hop that disagrees with the next.
2. **Evidence source.** `kubectl get endpointslices -l kubernetes.io/service-name=beacon -o yaml` is the hinge: it shows which pods the Service picked, on which port, and whether each is ready. Compare it with `kubectl get svc beacon -o yaml`, `kubectl get pods --show-labels -o wide` and the Events in `kubectl describe pod`.
3. **Discriminating command.** No endpoints at all: compare `kubectl get svc beacon -o jsonpath='{.spec.selector}'` with the pod labels. Endpoints ready but refused: compare the slice's port with `containerPort` and the "listening on" log line. Endpoints present but not ready: `kubectl describe pod <one>` and look for "Readiness probe failed", then ask Beacon itself (`kubectl exec … /ready`).
4. **Root cause and fix.** A: the Service selector says `component: beacon-api` but pods carry `component: api`; fix the selector. B: `targetPort: 8081` while Beacon listens on 8080; use `targetPort: http`. C: the readiness probe requests `/readyz`, which Beacon does not serve (404); set it to `/ready`. Never delete or weaken probes to make traffic flow.
