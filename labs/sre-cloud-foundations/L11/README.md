# L11 — Terraform generates Beacon's config: inputs, plan, state and the file on disk

Module M06 · ~120 min practical · profile `workstation` · **local providers only: no cloud, no cost**

## Ticket

> Beacon's per-environment config is generated by a small Terraform configuration
> (`hashicorp/local` writes the files, `hashicorp/random` gives each environment a stable
> deployment id). A teammate touched the dev workspace yesterday and nobody has run a plan since.
> Before anything is applied: find out what Terraform would do and why, get the workspace back
> to a no-change plan **without losing dev's deployment id**, and close the input-validation gap
> that let a broken sqlite config through last month.

## Objectives

- `obj-m06-01` write configuration with validated inputs, outputs and a dependency graph that
  passes `fmt` and `validate`
- `obj-m06-02` read a plan and predict what will be created, updated or replaced
- `obj-m06-03` tell configuration, state and the real object apart

## What is fixture-controlled

`setup.sh` copies `starter/` to `work/`, runs `terraform init` against the committed
`.terraform.lock.hcl` (read-only), applies the baseline (dev) and records the deployment id.
Then `inject.sh` changes the workspace in one of three ways chosen by the variant seed
(`LOOPED_VARIANT=variant-a|variant-b|variant-c`): an invalid input, a changed variable, or a
generated file that went missing out of band. Which one is yours to find from the plan.

Pinned: Terraform ≥ 1.9 (tested with 1.13.3), `hashicorp/local` 2.9.1, `hashicorp/random`
3.9.1. The lockfile carries hashes for darwin_arm64, darwin_amd64, linux_amd64 and linux_arm64.
State is the local file `work/terraform.tfstate`; there is no backend block and the lab guard
(`require_terraform_dir`) refuses one. (A team would use a remote backend; for S3 that means
`use_lockfile = true` for locking — DynamoDB-based locking is deprecated. Not in this lab.)

## Steps and checkpoints

**Checkpoint c1 — read before you apply (week 16, session 2).**

1. `bash labs/sre-cloud-foundations/L11/setup.sh`
2. Read `work/*.tf`, `work/templates/beacon.yaml.tftpl` and `work/terraform.tfvars`. Fill the
   *Configuration* section of `evidence/L11-notes.md`.
3. `terraform -chdir=labs/sre-cloud-foundations/L11/work state list` and `state show
   local_file.config`; `ls -l` and `shasum -a 256` the files under `work/out/`. Fill *State* and
   *Real object*. Where do the three disagree, if anywhere?
4. Write your *Plan prediction* (which resources, which action, which attribute forces it)
   **before** running `terraform -chdir=labs/sre-cloud-foundations/L11/work plan`. Then run it and
   explain any difference.

**Checkpoint c2 — fix, validate, test, graph (week 16, session 3).**

5. Fix what the ticket asks for. Apply only a plan you can explain; refuse one that replaces
   dev's deployment id. Finish with `terraform plan` saying **No changes**.
6. Add a validation rule so `store_kind = "sqlite"` with an empty `store_path` is refused at plan
   time (a validation block may reference another variable in Terraform 1.9+), and a
   `run` block in `work/tests/beacon.tftest.hcl` with `expect_failures` for it.
7. `terraform fmt -recursive`, `terraform validate`, `terraform test` (all in `work/`).
8. `terraform -chdir=labs/sre-cloud-foundations/L11/work graph > labs/sre-cloud-foundations/L11/evidence/L11-graph.dot`
   and say in your notes why `local_file.manifest` depends on both other resources.
9. `python3 labs/sre-cloud-foundations/L11/validate.py --explanation-file labs/sre-cloud-foundations/L11/evidence/L11-notes.md`
   and import `evidence/latest.json`.

## What you should observe

- Depending on the variant: a plan that stops at `Invalid value for variable` before comparing
  anything; a plan that wants to **replace** all three resources (read the `# forces
  replacement` markers and the `keepers` diff); or a plan that wants to **create** a resource
  that state says already exists (the refresh found the file gone).
- After the fix: `No changes. Your infrastructure matches the configuration.`, the same
  `deploy_id` as at setup, `terraform test` reporting 5 or more passed.

## What the validator checks

Local state only; the committed lockfile unchanged; `fmt`, `validate`, `test` (5+ runs, 3+
`expect_failures`, one for the sqlite rule); three bad inputs (`listen_port=80`,
`environment=prod`, sqlite without a path) each refused **by a validation rule** with every
other input known-good; a no-change plan; `out/dev/beacon.yaml` accepted by
`python3 -m beacon validate-config` with the checksum Terraform reports; the baseline
`deploy_id`; your graph and notes. Deleting validation rules, or applying a replacement and then
reverting, both fail on purpose.

## Rubric for the notes (self or mentor)

- Configuration, state and real object are described separately and the disagreement is named.
- The plan prediction was written first and names the forcing attribute or keeper.
- The fix is the smallest change that meets the ticket; anything refused is explained.

## Pause / resume

All state is in `work/` (config, state, generated files) and `evidence/`. `setup.sh` reuses an
existing `work/`. `reset.sh` destroys this workspace's three resources, saves your `.tf` files
in `.work-previous/` and rebuilds the workspace for the same variant.

## Lab versus production

- `local_file` stands in for any managed object: a file deleted by a cleanup job behaves like a
  bucket or DNS record deleted by hand — refresh notices, plan proposes to recreate.
- `random_id` with `keepers` is how identity-bearing values get tied to inputs; in production
  the replaced thing might be a database or a load balancer, and the plan line is identical.
- Real teams keep state in a remote backend with locking (S3 + `use_lockfile`) and run plans in
  CI; L12 and S12 go further.

## Limits — what this lab does not prove

It proves plan reading, input validation, `terraform test` with plan-only runs, the lockfile and
the configuration/state/object distinction on local files. It does not prove remote state,
locking under concurrency, provider credentials, import or modules (L12), and it never touches
a cloud API.
