# L13 hints (four rungs; rungs 3–4 end independent credit for this attempt)

1. **Boundary.** Separate three places a request can die: the build (what went into the image), the container start (what the process saw), and the path from your host into the container (what listens where). `docker ps -a` status and the first lines of `docker logs looped-l13-api` tell you which of the three you are in.
2. **Evidence source.** Compare the image's own description with the engine's: `docker image inspect looped-l13-beacon:1.4.0` (Config.User, Entrypoint, Os/Architecture), `docker port looped-l13-api`, `docker info --format '{{.Architecture}}'`, and what is actually inside: `docker run --rm --entrypoint ls looped-l13-beacon:1.4.0 -laR /app`.
3. **Discriminating command.** Host fails but container healthy: `docker logs looped-l13-api | grep listening` versus `docker port looped-l13-api`. Container exits: `docker run --rm --entrypoint ls looped-l13-beacon:1.4.0 -la /app/conf` versus `ls -la work/conf` and `cat work/.dockerignore`. Exec format error: `docker image inspect --format '{{.Os}}/{{.Architecture}}'` versus `docker info`.
4. **Root cause and fix.** A: Beacon binds 127.0.0.1 inside the container, so the published port reaches nothing; set `server.listen: 0.0.0.0` in work/conf/beacon.yaml and rebuild. B: `.dockerignore` excludes every `*.yaml`, so `conf/beacon.yaml` never enters the context; add `!conf/beacon.yaml` (do not delete .dockerignore — it keeps conf/.env.local out). C: the image was built for the other CPU architecture; `bash rebuild.sh` builds natively, and record the platform you verified.
