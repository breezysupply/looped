# L14 hints (four rungs; rungs 3–4 end independent credit for this attempt)

1. **Boundary.** Decide which promise is broken: the stack does not become ready, or it becomes ready but loses data when a container is replaced. `docker compose ps -a` (exit codes) and the last lines of each service's log separate the first from the second; for the second you have to run the persistence test yourself.
2. **Evidence source.** `docker compose config` is the file as Compose understood it: compare service names, the host in the store URL, each `depends_on` condition and health check, and every volume target. `docker inspect <container>` shows what actually happened: `State.Health`, `Mounts`, `Config.Env` (PGDATA).
3. **Discriminating command.** Name resolution: `docker compose run --rm --no-deps --entrypoint python3 api -c "import socket; print(socket.getaddrinfo('<host>', 5432)[0][4])"` for the URL's host versus `db`. Timing: compare the time of the api's FATAL line with the db's `ready to accept connections`. Data location: `docker inspect looped-l14-db-1 --format '{{json .Mounts}}'` against `PGDATA`.
4. **Root cause and fix.** A: the store URL names host `postgres` but the service is `db`; fix the URL. B: db has no health check and api waits only for `service_started`, so the api's bounded retry ends before the slow db listens; restore the `pg_isready` health check and `condition: service_healthy` (keep the fixture). C: the named volume is mounted at `/var/lib/postgres/data` while PostgreSQL writes to `/var/lib/postgresql/data` (an anonymous volume); mount `pgdata` at the real path and replace the db with `rm -fsv db && up -d --wait`.
