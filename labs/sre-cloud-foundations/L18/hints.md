# L18 hints (four rungs; rungs 3–4 end independent credit for this attempt)

1. **Boundary.** Two different gates: the API server decides what the bot may ask (authentication, then RBAC), and the CNI decides which packets a pod may send or receive. A Forbidden message comes from the first; a timeout or failed name lookup from the second. Never fix one by widening the other.
2. **Evidence source.** RBAC: the Forbidden line in `work/deploy-bot.log` names verb, resource and API group exactly; `kubectl auth can-i --list --as system:serviceaccount:beacon:beacon-deployer -n beacon` shows what the Role grants. Network: `assets/netcheck.sh` from inside the real pods, then `kubectl -n beacon describe networkpolicy` to see the selectors the API actually stored.
3. **Discriminating check.** For RBAC, ask `auth can-i` the one question the failing step needs (`watch deployments.apps`, `patch deployments.apps`, `list pods`). For the network, look at WHICH field fails: `"dns": "fail:…"` means the pod cannot reach CoreDNS (port 53 in kube-system); `"dns": "ok", "tcp": "timeout"` means DNS works but the path to the database is not allowed in one of the two directions. Check the labels the selectors use against `kubectl get pods,ns --show-labels`.
4. **Root cause and fix.** Variant A: the Role lacks `patch` on deployments, and the policy file has no DNS egress rule at all — add `patch` only, and an egress rule to `k8s-app: kube-dns` in `kubernetes.io/metadata.name: kube-system` on UDP and TCP 53. Variant B: the Role lacks `watch` on deployments; the DNS rule selects the namespace by `name: kube-system`, a label that does not exist — use `kubernetes.io/metadata.name`. Variant C: the Role lacks `list` on pods; the database's ingress rule allows `app: api` instead of `app: beacon-api`.
