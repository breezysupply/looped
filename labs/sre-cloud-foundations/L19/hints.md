# L19 hints (four rungs; rungs 3–4 end independent credit for this attempt)

1. **Boundary.** Decide where the change fails: on your laptop (rendering against the schema and templates, before any API call), in the API server (object rejected), or on the nodes (object accepted, pods cannot start). Each leaves different evidence, and only the last one creates a failed revision.
2. **Evidence source.** Helm's own error text names a JSON path when the schema refuses a value. For a rollout that times out, `helm history beacon`, `kubectl get pods -o wide` and the first Warning in `kubectl describe pod <new pod>` say what the kubelet tried. `docker images looped-l19-beacon` lists the builds that exist.
3. **Discriminating check.** Render the change locally: `helm template beacon work/chart -n beacon -f work/chart/values-staging.yaml -f work/change/values-1.5.0.yaml --show-only templates/deployment.yaml`. If that fails, the value is wrong. If it renders, compare the rendered `image:` with what was built and loaded into the nodes, character by character.
4. **Root cause and fix.** Variant A: `limits.memory: 192` is a number (bytes to Kubernetes); write `"192Mi"`. Variant B: tag 1.5.1 was never built; roll back to the last good revision, set `tag: "1.5.0"` and upgrade. Variant C: `registry.lab/beacon` does not exist for the nodes; use `repository: looped-l19-beacon`, roll back the failed revision first. Then the drill: `helm rollback beacon 1 --wait`, check `/version` says 1.4.0, roll forward to 1.5.0, `helm test`.
